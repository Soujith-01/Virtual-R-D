# Virtual R&D Lab

**AI-Powered Experimental Discovery Platform** — explore experimental possibilities before spending money on real experiments.

Ask a research question in plain language. The agent retrieves process knowledge, generates candidate experiments, predicts their outcomes with a trained machine-learning model, ranks them with a transparent score, simulates the winner in a virtual reactor, and proposes the next experiment.

```
Research Question
      ↓
Scientific Knowledge Retrieval        (sentence-level semantic search)
      ↓
AI Experiment Generation              (model-guided search + diversity filter)
      ↓
ML Outcome Prediction                 (Random Forest, trained in this repo)
      ↓
Experiment Ranking                    (transparent weighted score)
      ↓
Virtual Experiment Simulation         (6-stage reactor timeline)
      ↓
AI Research Report                    (grounded narrative + caveats)
      ↓
Next Suggested Experiment             (neighbourhood probe)
```

---

## ⚠️ Scientific disclaimer

**The prediction model is trained on a SIMULATED prototype dataset** (`synthetic_prototype_v1`, 3 000 rows generated by an authored surrogate in `backend/domain.py`).

* Predictions demonstrate an AI-driven discovery **workflow**. They are **not** validated real-world chemical results.
* `confidence` and intervals are **model-derived uncertainty proxies** (tree disagreement + residual spread), **not** calibrated statistical guarantees.
* The virtual reactor is a **visual simulation**, not a laboratory control system.
* Knowledge-base notes in `backend/rag/documents/` are **authored prototype content for this demo** — not publications, no authors, no DOIs, and not citable as scientific literature.

The architecture is deliberately built so a validated in-house dataset can replace the prototype one and the model retrained **without touching the API or the UI** (see [Replacing the dataset](#replacing-the-prototype-dataset)).

## Quick start

Two terminals. Both commands matter, in this order.

### 1. Backend

```bash
cd backend

# first time only: create the dataset and train the model
python training/generate_dataset.py     # writes training/dataset.csv
python training/train_model.py          # writes models/experiment_model.pkl

# run the API
python -m uvicorn main:app --reload
```

API: <http://127.0.0.1:8000> · Interactive docs: <http://127.0.0.1:8000/docs>

Install dependencies first if needed:

```bash
cd backend
python -m pip install -r requirements.txt
```

### 2. Frontend

```bash
cd frontend
npm install
npm run dev
```

Dashboard: <http://127.0.0.1:5173>

### 3. Demo

Open the dashboard and either click **▶ Run one-click demo**, or:

1. **Start new research**
2. Keep the default objective: *"Maximize reaction yield while minimizing reaction time."*
3. **Generate experiments** → watch the 10-stage agent pipeline run
4. Inspect the five ranked candidates and the comparison charts
5. **Start virtual experiment** → the animated reactor walks through all six stages
6. Read the research report and the next suggested experiment

The full demonstration runs in well under 60 seconds (agent ≈ 2 s, reactor animation ≈ 13 s).

> **Note — paths containing `&`:** if the project folder path contains `&` or spaces, Windows `cmd`
> can fail to resolve `node_modules/.bin` shims. The `npm` scripts here therefore invoke Vite
> through `node ./node_modules/vite/bin/vite.js` directly, which is immune to that problem. The
> shortcuts `node ./node_modules/vite/bin/vite.js dev` and `... build` always work too.

## Machine-learning model

Trained in `backend/training/train_model.py` — a scikit-learn `Pipeline`:

```
ColumnTransformer( OneHotEncoder(catalyst) + passthrough(4 numeric) )
    → RandomForestRegressor(n_estimators=300, min_samples_leaf=2, max_features=0.7)
```

### Evaluation (held-out 20 % test split, 600 rows)

| Metric | Value | Meaning |
| --- | --- | --- |
| **R²** | **0.9648** | 96.5 % of yield variance explained |
| **MAE** | **3.12** | average error is 3.1 yield points |
| **RMSE** | **4.07** | penalises larger errors |
| **5-fold CV R²** | **0.9654 ± 0.0017** | stable across folds, not a lucky split |

### Feature importance (grouped)

| Feature | Importance |
| --- | --- |
| concentration | 34.4 % |
| catalyst | 31.1 % |
| temperature | 28.7 % |
| reaction_time | 4.7 % |
| pressure | 1.2 % |

`reaction_time` and `pressure` score low because their effects **saturate** — that is the correct
signal, and it is exactly why ranking on yield alone would pick a slow, hot, expensive run.
`pressure` importance is discussed in `rag/documents/03_pressure_and_headspace.md`.

### Uncertainty handling

The ensemble's per-tree predictions give a free disagreement signal:

* `uncertainty_std` — standard deviation across the 300 trees (yield points)
* `estimated_confidence` — `clip(1 − std / 25, 0.05, 0.99)`, explicitly labelled a **proxy**
* `interval_low` / `interval_high` — `± 1.645 × √(residual_std² + tree_std²)`, labelled **approximate**

No endpoint ever presents these as statistical certainty.

## Experiment ranking (never yield-only)

`backend/services/scoring.py` parses the free-text objective into priorities, then builds weights:

| Component | Meaning | Baseline weight |
| --- | --- | --- |
| `yield` | predicted yield (%) | 1.00 |
| `time` | `100 × (1 − normalised reaction_time)` | 0.70 |
| `temperature` | milder operating temperature | 0.40 |
| `pressure` | lower pressure | 0.30 |
| `risk` | `100 − risk penalty` | 0.60 |

Objective keywords multiply those weights (e.g. *"minimizing reaction time"* → ×2.4 on `time`), then
everything is normalised to sum to 1. `score = Σ weightᵢ × componentᵢ`, and every component, weight,
contribution and a plain-language `reason` are returned to the client.

Risk is a heuristic penalty (0–100) over: model disagreement, operating-envelope breaches, extreme
single variables (T > 150 °C, P > 8 bar, t > 150 min, C > 0.45 M) and low-information regions.

**Demonstration of why this matters:** for the default objective the winner is *80 °C / 2.5 bar / catalyst B / 0.19 M / 20 min → ~78 % yield, score ~84*, while a higher-yield candidate at 90 min scores lower because it costs 4.5× the reactor occupancy. Ranking on yield alone would pick the wrong experiment.

## Configuration

Copy `backend/.env.example` → `backend/.env`. **No secrets are hardcoded anywhere**, and every value
has a safe default, so an empty config still runs the whole demo.

### Running without an LLM (default)

With `LLM_PROVIDER=none`, narration uses a **deterministic template** engine. It produces the same
factual content — grounded in the retrieved passages, naming its sources — just phrased
programmatically. The report and `/health` both state which backend was used.

### Enabling an external LLM

`backend/services/llm.py` is a single OpenAI-compatible client, so any of these works:

```bash
# OpenAI
LLM_PROVIDER=openai
LLM_MODEL=gpt-4o-mini
LLM_API_KEY=sk-...

# Groq (OpenAI-compatible)
LLM_PROVIDER=groq
LLM_MODEL=llama-3.1-8b-instant
LLM_API_KEY=gsk_...

# Local Ollama (no key needed)
LLM_PROVIDER=ollama
LLM_MODEL=llama3.1
LLM_BASE_URL=http://localhost:11434
```

The LLM only *narrates*. Every number, ranking and simulation is computed locally, and prompts
forbid inventing citations; output that fabricates publication metadata is rejected and the
template is used instead.

### Retrieval backends

| Backend | Install | Notes |
| --- | --- | --- |
| sentence-transformers + FAISS | `pip install -r backend/requirements-rag.txt` | semantic embeddings, ~2 GB (PyTorch) |
| TF-IDF + NumPy (fallback) | already installed | offline, instant, no download |

`EMBEDDING_BACKEND=auto` picks sentence-transformers when importable and falls back to TF-IDF
otherwise — including when the model cannot be downloaded. Either way the retriever returns
**source names with every chunk**, and the active backend is reported in `/health` and the UI.
PDF ingestion additionally needs `pypdf` (in `requirements-rag.txt`).

## Replacing the prototype dataset

The synthetic surrogate is isolated in `backend/domain.py`. To move to real data:

1. Put your measurements in `backend/training/dataset.csv` with columns
   `temperature, pressure, catalyst, concentration, reaction_time, yield`
   (extra columns are ignored; `catalyst` values must be `A`, `B`, `C`, `D` or `None`).
2. Adjust `RANGES` / `SAFE_ENVELOPE` in `backend/domain.py` if your envelope differs.
3. Retrain:

   ```bash
   cd backend
   python training/train_model.py
   ```

4. Restart the API. `/health`, `/model-info` and the UI model card report the new metrics and
   provenance automatically.

No API, scoring or frontend change is required. Replace `backend/rag/documents/` with real licensed
source material and run `python -m rag.retriever --rebuild` to ground the explanations in it.

## Known limitations / remaining issues

1. **Synthetic training data.** The headline limitation — see the disclaimer above. Metrics are
   in-sample to the surrogate, not evidence about real chemistry.
2. **No persistence of manual predictions.** `/predict` and `/simulate` are stateless; only
   `/research` runs are stored in SQLite.
3. **Simulator fidelity.** The reactor timeline is a visualisation with plausible curves
   (first-order heating, saturating pressure, first-order conversion), not a thermodynamic model.
   Its `observed_yield` comes from the same authored surrogate family as the training data, so
   prediction-vs-measurement agreement is **not** independent validation.
4. **Pressure importance is low (1.2 %).** Expected — the effect saturates across most of the
   range. It remains a scored component so a pressure-minimising objective can change the ranking.
5. **Bundle size.** The production build is ~880 kB raw (~238 kB gzipped), mostly Recharts. Fine
   for a local demo; code-split before deploying.
6. **Heavy retrieval stack not installed by default.** Semantic embeddings are one
   `pip install -r backend/requirements-rag.txt` away; until then retrieval is lexical (TF-IDF).
7. **Single-process assumptions.** The model store and index are in-process caches; `--reload`
   rebuilds them. Fine for a demo, not for horizontal scaling.
8. **`confidence` is a heuristic.** `clip(1 − std/25, 0.05, 0.99)` is deliberately conservative and
   clearly labelled; it is not a calibrated probability.
